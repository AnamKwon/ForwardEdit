# Long inference and direct weight analysis

Use this path when the original small FP32 analysis limits cannot represent the actual model or long generated reasoning. The user still chooses the task; no successful layer, neuron, direction or coefficient is a default.

`research.json` is immutable once the ledger starts. Bind original checkpoint, tokenizer/config/static file hashes, development dataset, decoder, dtype, attempt/success/artifact limits before the first research forward. Hardware setup controls have their own ledger and never count toward the scientific budget.

For Qwen3.5 text checkpoints with default RoPE, an opt-in
`native_precision_load: true` avoids the transient full CPU FP32 parameter copy
before BF16 inference. It requires source dtype provenance and text-only BF16
Transformers execution. Published FP32 parameters are restored directly from
checkpoint values before casting; floating positional buffers must remain FP32.
The default loading path is unchanged. Record this setting before the ledger
starts, retain operational amendments, and verify effective parameter/buffer
identity. Reduced loading memory does not change the inference-only contract or
certify performance equivalence on a benchmark. Other architecture/RoPE variants
are currently rejected by this optional loader.

Apply [data separation](data-separation.md) before task observations. Use `discovery` for edit/train construction and `validation` for candidate selection; both wire splits are readable development data, not sealed final tests. The loader rejects cross-split duplicate normalized prompts/tokens and repeated optional `group_id` values. Image inputs are compared using image byte hashes as well as text/tokens. Group related variants before splitting and record actual exposure separately. Final research evaluation requires a frozen, host-controlled follow-up; the loader does not enforce an OS sandbox or scientific independence across workspaces.

For native Gemma 3 image-and-text generation, add a `multimodal` object with `kind: "gemma3"`, `vision_checkpoint`, `config`, and `processor_dir`, all using workspace-relative paths. The ordinary model checkpoint remains the verified text component. The vision checkpoint contains the matching official `vision_tower.*` and `multi_modal_projector.*` tensors. The config file contains the full Gemma 3 configuration. Native attachment requires Transformers 5.22 or later and the local Gemma image processor. Vision weights remain frozen while the existing candidate API edits the source-bound text component.

Image examples provide `prompt` and an `images` list of local paths. The native processor creates image placeholders, pixels and token types. Every selected image and processor file is hash-bound to the forward snapshot. Pixel shapes, preprocessing hashes and source images are retained in an `image_preprocessing` artifact shared by both model conditions. Pixels enter only the cache prefill. Image replay with explicit `tokens` preserves the processor prompt prefix and appends text token types for the continuation. Image inputs currently use Transformers generation. Keep actual image-task scores and text-only scores explicit.

`observations.module_inputs` selects up to eight named linear or vector-normalization input modules. These are saved as `module_inputs` artifacts, with actual token positions. They can expose a normalization input that intervenes between an affine write and a residual sum. They are distinct from affine-writer input evidence consumed by `research_prepare_edit`. Multimodal observations retain source text-module names and record the shared instance's actual full-model paths. Native BF16 parameter exports widen values exactly to FP32 on CPU and report both source and exported dtypes.

- `research_forward(spec)` starts one serial asynchronous MCP inference job. `type` is `generate` or `teacher_forced`; `model` is `original`, `edited`, or generation-only `both`. Specify exact development `split`, `ids`, candidate when edited, `n`, and generation limit. Both-model generation uses matched per-item random seeds. Status polling consumes no forward budget. Keep failed attempts, successful logical passes, sequences, generated tokens and observed execution calls separate.
- `research_status(job_id)` and `research_result(job_id)` retain terminal success or errors. Only a verified successful real job spends a successful pass. A paired generation batch remains one logical pass and contains two engine submissions. vLLM engine submissions are **not** a count of internal autoregressive network invocations.
- Transformers generation can expose advisory `research_status.progress` counters for the active model, completed samples, total samples and generated tokens. Progress can lag the worker and does not verify the result or spend a successful pass. Older jobs and the vLLM backend may not have these counters.
- Optimized vLLM generation supplies actual completions and verifies actual loaded GPU edit tensors. Teacher-forced Transformers inference supplies actual residual/MLP inputs and token log probabilities. These have different kernels; never treat their sampled outputs as interchangeable baselines. Use the same generation backend for each comparison and final confirmation.
- `observations` selects explicit residual `layers`, `mlp_layers`, per-ID token `positions`, and optional `mean_answer_tokens` (up to8192). vLLM generation does not expose hooks. Instead call `research_make_contexts` on a completed generation, then teacher-forced observation on its source-bound generated prefixes. Keep pooled means distinct from individual token trajectories.
- For Transformers generation, `observations.first_token_ids` records the raw first-step logits for 1–32 explicit vocabulary IDs before sampling in the actual generation batch. The `first_token_logits` artifact lists the requested IDs in column order and identifies rows by item and sample. Its logits reflect the generation path and exclude temperature and sampling filters.
- An unedited runtime control can specify `first_token_logit_bias`, a list of 1–32 objects with caller-selected `token_id` and finite signed `bias` in [-100,100]. Transformers generation adds these values only at the first generated position, before sampling. Subsequent positions and model weights are unchanged. Raw logit observations remain before this adjustment; the source-bound spec records the steering policy. Keep runtime steering results distinct from parameter edits and do not search biases on an independent test.
- `observations.generation_logits` takes `{"token_ids":[...],"positions":{"example-id":[...]}}` for the same raw scores at later zero-based continuation offsets. It accepts 1–32 distinct token IDs and up to 16 offsets per selected example. The artifact identifies each live sample, its offset and its actual chosen token. Offsets after a sample ends have no row.
- `research_compare_generations` writes paired token divergence, exact suffix repetition statistics, and completion counts from verified generation jobs. Optional `final_answer_envelope` checks the last line against the recorded extracted answer using literal delimiters. It preserves the original grades. With `research_make_contexts`, optional `continuation_lengths` retains the full prompt and an exact prefix of the specified `sample`.
- `research_read_generations` returns bounded saved snippets and `research_read_array` reads explicit coordinates from hash-bound arrays. `research_export_tensor` exports exact stored weights to a hash-bound NumPy file for CPU inspection. For tensors over the 16M-entry cap, supply a bounded slice as half-open `ranges` for every stored axis. Use the returned source shape and ranges to interpret the exported coordinates. CPU matrix algebra may summarize observed activations. Loss fitting, finite differences and coordinate or coefficient sweeps remain forbidden.
- `research_prepare_edit` takes the caller's explicit source-bound plan, tensor/rows/columns, verified observation contexts, desired output direction, rationale and controls. It supports full output width up to4096 and at most256 selected columns/262144 values. It computes signed local contributions and proposed deltas with the recorded inference dtype. Supply both failure and reference contexts, pairing justification, value derivation, alternative explanation, predicted effect, disconfirmation, controls and a reference-output bound. `ready_for_causal_probe` confirms local evidence/arithmetic only; changed future activations and downstream nonlinear effects require actual inference.
- Commit the chosen plan with `create_candidate` or `revise_candidate`, then observe parent/child feedback. A nonzero FP32 file delta may vanish in BF16: actual GPU verification must reject that as an effective edit. Preserve original FP32-sensitive parameters/buffers. Do not cast every tensor indiscriminately.

Freeze one eligible candidate and the full protocol before independent data access. Report mathematical answer accuracy, previously correct answers lost, reference NLL/token accuracy, unparsed answers and uncertainty. Fewer repetitions or shorter thinking alone do not establish improved mathematics. Analysis capacity (for example150 actions) and50 successful forwards are research budgets, not150 edits or50 epochs; do not fill them with redundant requests.

For `research_prepare_edit`, use the exact `basis` keys: `failure_description`, `structural_role`, `mechanism_hypothesis`, `pairing_justification`, `value_derivation`, `alternative_explanation`, `expected_behavior`, and `disconfirming_result` are nonempty strings. `controls` is a nonempty list of objects with `kind` and `purpose`. `max_reference_output_delta` is a finite numeric bound on the selected affine output's Euclidean delta, in state units. A sentence giving a logit or probability bound has different units and does not fill this field; document both separately when needed.

Read every returned `decision` and `reasons`. Missing keys, wrong types or exceeded bounds require correction or a revised hypothesis before presenting the proposal as prepared. Preserve the original defer record. If a low-level exploratory edit was already executed, disclose that timing and distinguish later schema review from pre-edit approval; do not relabel the earlier event. A structurally valid record still does not certify the semantic role or performance.

For a fixed host-authored sequence, [research_schedule.py](../../../scripts/research_schedule.py) accepts a JSON object with `steps`, each containing a unique file-safe `name` and explicit `spec`. Run it with `--workspace`, `--schedule`, and a dedicated `--receipts` directory, using the interpreter with the project's MCP/model dependencies and the designated `CUDA_VISIBLE_DEVICES`. It keeps one MCP connection, saves the job ID before waiting, and reattaches to existing jobs when resumed. A timeout leaves the server job live; an ambiguous lost submission reply is retained for reconciliation rather than automatically resubmitted. The server still enforces the shared study budget. This client performs no parameter choice or fitting.

Current API supports `model: both` for generation only. Teacher comparisons require two explicit steps, `model: original` and `model: edited`, and consume two successful-forward slots. The schedule client preflights all specs with the server's read-only validator. Preserve original/edited artifact identity when combining teacher results; do not pretend two teacher jobs are one successful pass.
