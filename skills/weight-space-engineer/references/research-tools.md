# Long inference and direct weight analysis

Use this path when the original small FP32 analysis limits cannot represent the actual model or long generated reasoning. The user still chooses the task; no successful layer, neuron, direction or coefficient is a default.

`research.json` is immutable once the ledger starts. Bind original checkpoint, tokenizer/config/static file hashes, development dataset, decoder, dtype, attempt/success/artifact limits before the first research forward. Hardware setup controls have their own ledger and never count toward the scientific budget.

- `research_forward(spec)` starts one serial asynchronous MCP inference job. `type` is `generate` or `teacher_forced`; `model` is `original`, `edited`, or generation-only `both`. Specify exact development `split`, `ids`, candidate when edited, `n`, and generation limit. Both-model generation uses matched per-item random seeds. Status polling consumes no forward budget. Keep failed attempts, successful logical passes, sequences, generated tokens and observed execution calls separate.
- `research_status(job_id)` and `research_result(job_id)` retain terminal success or errors. Only a verified successful real job spends a successful pass. A paired generation batch remains one logical pass and contains two engine submissions. vLLM engine submissions are **not** a count of internal autoregressive network invocations.
- Optimized vLLM generation supplies actual completions and verifies actual loaded GPU edit tensors. Teacher-forced Transformers inference supplies actual residual/MLP inputs and token log probabilities. These have different kernels; never treat their sampled outputs as interchangeable baselines. Use the same generation backend for each comparison and final confirmation.
- `observations` selects explicit residual `layers`, `mlp_layers`, per-ID token `positions`, and optional `mean_answer_tokens` (up to8192). vLLM generation does not expose hooks. Instead call `research_make_contexts` on a completed generation, then teacher-forced observation on its source-bound generated prefixes. Keep pooled means distinct from individual token trajectories.
- `research_read_generations` returns bounded saved snippets; `research_read_array` reads explicit coordinates from hash-bound arrays. `research_export_tensor` exports an exact stored tensor (up to16M entries) to a hash-bound NumPy file for CPU-only inspection. Exported weights are evidence, not replacement files. CPU matrix algebra may summarize observed activations; fitting weights to loss, finite differences and blind coefficient sweeps remain forbidden.
- `research_prepare_edit` takes the caller's explicit source-bound plan, tensor/rows/columns, verified observation contexts, desired output direction, rationale and controls. It supports full output width up to4096 and at most256 selected columns/262144 values. It computes signed local contributions and proposed deltas with the recorded inference dtype. Supply both failure and reference contexts, pairing justification, value derivation, alternative explanation, predicted effect, disconfirmation, controls and a reference-output bound. `ready_for_causal_probe` confirms local evidence/arithmetic only; changed future activations and downstream nonlinear effects require actual inference.
- Commit the chosen plan with `create_candidate` or `revise_candidate`, then observe parent/child feedback. A nonzero FP32 file delta may vanish in BF16: actual GPU verification must reject that as an effective edit. Preserve original FP32-sensitive parameters/buffers. Do not cast every tensor indiscriminately.

Freeze one eligible candidate and the full protocol before independent data access. Report mathematical answer accuracy, previously correct answers lost, reference NLL/token accuracy, unparsed answers and uncertainty. Fewer repetitions or shorter thinking alone do not establish improved mathematics. Analysis capacity (for example150 actions) and50 successful forwards are research budgets, not150 edits or50 epochs; do not fill them with redundant requests.

For `research_prepare_edit`, use the exact `basis` keys: `failure_description`, `structural_role`, `mechanism_hypothesis`, `pairing_justification`, `value_derivation`, `alternative_explanation`, `expected_behavior`, and `disconfirming_result` are nonempty strings. `controls` is a nonempty list of objects with `kind` and `purpose`. `max_reference_output_delta` is a finite numeric bound on the selected affine output's Euclidean delta, in state units. A sentence giving a logit or probability bound has different units and does not fill this field; document both separately when needed.

Read every returned `decision` and `reasons`. Missing keys, wrong types or exceeded bounds require correction or a revised hypothesis before presenting the proposal as prepared. Preserve the original defer record. If a low-level exploratory edit was already executed, disclose that timing and distinguish later schema review from pre-edit approval; do not relabel the earlier event. A structurally valid record still does not certify the semantic role or performance.

For a fixed host-authored sequence, [research_schedule.py](../../../scripts/research_schedule.py) accepts a JSON object with `steps`, each containing a unique file-safe `name` and explicit `spec`. Run it with `--workspace`, `--schedule`, and a dedicated `--receipts` directory, using the interpreter with the project's MCP/model dependencies and the designated `CUDA_VISIBLE_DEVICES`. It keeps one MCP connection, saves the job ID before waiting, and reattaches to existing jobs when resumed. A timeout leaves the server job live; an ambiguous lost submission reply is retained for reconciliation rather than automatically resubmitted. The server still enforces the shared study budget. This client performs no parameter choice or fitting.

Current API supports `model: both` for generation only. Teacher comparisons require two explicit steps, `model: original` and `model: edited`, and consume two successful-forward slots. The schedule client preflights all specs with the server's read-only validator. Preserve original/edited artifact identity when combining teacher results; do not pretend two teacher jobs are one successful pass.
