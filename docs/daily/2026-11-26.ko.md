## 방향 결정
- 데이터 표기를 확인하기 전에 "약점"을 정하지 않습니다. 앞으로 약한 벤치마크 목표는 오류 행을 직접 읽어 표기를 점검한 뒤 고릅니다.
- BFCL 호출 삼가기는 "주어진 도구로 답할 수 없다" 행만 정답 표기로 씁니다. 별도 400행은 편집기와 LoRA 모두 보지 않은 검증용으로 남겼습니다.
- 사용자 요청으로 LLM 편집 v3의 예산을 24패스에서 48패스로 늘렸습니다. 편집 실험을 시작하기 전에 바꾼 것이며, 데이터와 동결 기준은 그대로입니다. LoRA와는 같은 데이터 200행으로 비교합니다.
- 실제 BFCL 테스트는 LLM 편집 결과가 나온 뒤, 통과한 방법을 원본과 함께 한 번만 평가합니다.

## 프로토콜 이탈 기록
- v1 데이터 설계 결함: 고칠 행이 원본이 이미 맞힌 행 위주였습니다. 사전 등록 문서에 공개했습니다.
- v2(오류 행 중심)는 시작하지 않았습니다. 첫 턴 glaive 행의 표기 문제 때문에 목표를 "도구 없이 답하기"에서 A2 지시 답으로 바꿨습니다. A2가 오류 254행 중 21행에서만 평문으로 답해 데이터가 부족했습니다.
- 공용 디스크가 가득 찼습니다. 원인은 호스트 LoRA 스크립트가 rank-8 결과를 꽉 찬 fp32 행렬(파일당 8.5GB)로 저장한 것입니다.
  - 이 때문에 v3 LoRA 1e-4 학습 저장과 첫 편집 실행 시작이 실패했습니다. 편집 실행은 세션 시작 전에 실패했습니다.
  - 기존 파일은 float64 SVD로 rank-8 인자로 바꿨습니다. 상대 오차는 약 1e-7이고, 합친 bf16 모델은 99.999% 이상 동일합니다. 확인을 통과한 파일만 원본을 지웠습니다.
  - 이후 LoRA는 인자 형태로 저장하고, 1e-4는 다시 학습했습니다.
- v3 확인 세트는 사전 등록한 분할 규칙대로 나눠서 11행뿐입니다.
