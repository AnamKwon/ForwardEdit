# LLM 가중치 편집의 데이터 분리

[English](EDIT_EVALUATION_PROTOCOL.md)

LLM 편집도 파인튜닝처럼 변경을 만드는 데 쓴 데이터와 전이를 평가할 데이터를
분리해야 합니다. 편집 산식에 사용한 문항의 점수 상승은 개발 결과이며, 검증
일반화 결과가 아닙니다. [추론 전용 계약](INFERENCE_ONLY_CONTRACT.md)은 그대로
적용합니다. LLM이 CPU 산술을 명시하는 절차이며 학습을 허용하는 규칙이 아닙니다.

## 편집 전에 고정할 데이터 역할

| 구분 | 용도 | 가중치를 설계하는 편집자의 접근 |
|---|---|---|
| 편집용 train (`discovery`) | 정답·오류·활성 분석, 편집 설계와 피드백 재수정 | 허용 |
| 후보 선택용 validation (`validation`) | 고정 지표로 명시한 후보 평가·선택 | 선택 지표만 사용, 문항별 오류를 편집 산식에 사용하지 않음 |
| 최종 test | 고정 후보와 선언한 원본 기준선 비교 | 후보 고정 후 공개, 편집·재선택에 피드백하지 않음 |

세 역할로 나누면 반복적인 검증 선택을 최종 일반화로 오인하지 않습니다. 두 집합만
쓰는 편집용 train–holdout 방식도 가능합니다. 단, 두 번째 집합을 보기 전에 후보
하나를 고정하고, 그 결과로 후보를 선택하거나 바꾸지 않아야 합니다. 파일명이나
API의 split 이름으로 독립성을 판단하지 말고 실제 설계와 사용 이력을 기록합니다.

1. 적절한 공식 분할을 쓰거나 모델 오류를 관찰하기 전에 고정 원본 풀을 분할합니다.
   출처·버전 해시, ID, 개수, 배정 규칙과 시드를 저장합니다. 제외 기준과 기존 노출도
   결과를 보기 전에 기록합니다.
2. 독립성 단위에 따라 중복·변형을 묶습니다. 예를 들어 원문 문제의 패러프레이즈나
   같은 이미지의 여러 질문을 하나의 그룹으로 취급할지 정합니다. 생성 문항은 편집
   데이터와 템플릿을 공유하는지 밝힙니다. 원본·편집 점수를 보고 유리한 오류만 골라
   검증·테스트 집합을 만들지 않습니다.
3. 편집 설계·재수정은 train 데이터에서만 합니다. 해당 점수와 validation 점수를
   분리하고, 사전 기준으로 validation에서 후보를 고릅니다. validation의 오류·정답·
   활성 벡터를 다음 편집에 넣었다면 개발 데이터로 전환한 사실을 밝힙니다. 이후
   같은 문항을 다시 평가한 점수는 독립 검증이 아닙니다.
4. 최종 평가 전에 선택한 패치, 원본·부모, 데이터 manifest, 프롬프트·토크나이저,
   디코더·정밀도·토큰 상한, 채점기·기준선·판정 기준을 고정합니다. 같은 문항을 같은
   조건에서 원본과 편집본에 평가합니다.
5. 최종 목표 정확도, 기존 정답 손실, 상한 도달, 비대상 과제 보존을 나눠 보고합니다.
   순점수 개선과 보존 기준 실패는 동시에 존재할 수 있습니다. 최종 결과를 보고
   편집을 조정하거나 차점 후보로 바꾸지 않습니다.

비율 하나를 모든 연구에 강제하지 않습니다. 실제 문항·그룹 수와 불확실성을 보고하며,
같은 문제의 여러 생성은 독립 문제 수에 더하지 않습니다. 노출한 집합을 복사하거나
이름을 바꿔도 비노출 상태로 돌아가지 않습니다. 이미 본 풀을 사후 재분할해 독립
검증이라고 부를 수 없습니다.

## MCP에 적용하는 방법

첫 과제 관찰 전에 [편집자용 데이터 분리 지침](../skills/weight-space-engineer/references/data-separation.md)을
읽습니다. research의 `discovery`는 편집용 train, `validation`은 후보 선택용으로
매핑합니다. 두 집합은 개발 도구로 읽을 수 있으므로 최종 데이터 접근은 호스트가
별도로 관리합니다. API 표기와 별개로 실제 과학적 역할과 노출 이력을 남깁니다.

research 로더는 split 사이의 동일한 정규화 프롬프트·토큰 입력과 동일한 `group_id`를
거부합니다. 이미지 입력은 텍스트/토큰과 이미지 바이트 해시를 함께 비교합니다.

```json
{"id":"problem-17-paraphrase-2","group_id":"problem-17","prompt":"…","answer":"…"}
```

이 `group_id`를 공유하는 변형은 한 split에 둡니다. 사전 검사는 현재 읽는 데이터셋에
한정되며 의미적 패러프레이즈 발견, 기록하지 않은 과거 노출, 다른 작업공간의 모든
파일 검사나 OS 격리를 보장하지 않습니다. 개발·최종 작업공간을 따로 써도 호스트는
manifest에서 중복과 원본 그룹을 확인해야 합니다. 기존 FP32 확인 경로는 처음 봉인한
최종 파일을 검사합니다. research BF16의 최종 평가는 호스트가 관리하는 고정 후속
작업공간과 누적 예산을 사용합니다. 중복 검사를 추가한 것만으로 서버가 모든 최종
test 접근을 강제 차단한다고 설명하면 안 됩니다.

## 보고서의 필수 분리

| 데이터 역할 | 문항/그룹 수 | 편집 산식에 사용 | 후보 선택에 사용 | 원본 | 고정 편집 | 정답 증가/손실 | 상한 도달 |
|---|---|---|---|---|---|---|---|
| 편집용 train | 명시 | 예 | 명시 | 측정 | 측정 | 측정 | 측정 |
| 선택용 validation | 명시 | 아니요 | 예 | 측정 | 측정 | 측정 | 측정 |
| 최종 test | 명시 | 아니요 | 아니요 | 측정 또는 미측정 | 측정 또는 미측정 | 측정 | 측정 |

출처·분할·패치 해시, 대조군, 생성 설정·정밀도, 문항별 원본 대비 변화와 노출 한계를
남깁니다. 사례 보고서에는 **Unaddressed criticisms / 미대응 비판**을 포함합니다.
파일명을 바꿔 과거 점수를 다른 역할로 옮기지 않습니다. 앞으로의 실행 규칙이며,
역사적 실험을 재등록하거나 새 모델 측정값을 만드는 문서가 아닙니다.
